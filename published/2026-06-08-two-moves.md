# Two Moves

The entire identifier grammar reduces to two structural moves. Dot walks the tree. Underscore opens a property bag. That is the whole language for navigating and describing the fabric.

Dot is tree navigation. `xpath.data.uri` — three segments, each namespaced by its parent. The parent defines the child. The path *is* the qualification. What the relationship between parent and child means shifts depending on what both are. `xpath` to `data` — a system contains a domain. `data` to `uri` — a domain contains a sub-protocol. `uri` to `get` — a protocol defines an operation. Three different relationships, same dot grammar. The schemas at both ends tell you what kind of relationship it is.

Underscore is the other move. It opens a property bag at the current node — a lateral move, not a deeper one. The bag is *at* the node, not *below* it. Inside the bag, property names get their namespace from the bag's AVRO schema, not from tree position. `_server` means: open the server property bag at the current node. The prefix switches namespace resolution from tree-positional to schema-assigned. No overlap between the two. Dot walks the address space. Underscore opens the property space.

The namespace switch is where it gets interesting. A property bag has a physical data schema that assigns namespace to the short names within it. Property names inside the bag can themselves form an identifier tree with their own property bags attached — and this is recursive. Same grammar at every level. The distinction between data and metadata is not structural. It is a schema distinction. Content is a property whose schema namespaces it as content. Metadata is a property whose schema namespaces it as metadata. The fabric does not know the difference. The schemas do.

This gives a clean test for what belongs where. Operators that a protocol *defines* — `get`, `put`, `delete` — are part of the protocol's identity. They belong in the tree, dot-navigated, namespaced by position. Without them, it is a different protocol. Operators that are *applied to* a node — `_is`, `_noop` — come from outside. They are not part of what makes the node what it is. Any node can be asked `_is`. These belong in property bags, underscore-navigated, namespaced by schema. One test distinguishes them: does this operator exist because this specific node declares it, or because a schema brought it from a base interface?

AVRO carries both dimensions simultaneously on the same identifier. The physical schema assigns namespace — it says what is there. The logical type activates functional capability — it says what can be done. "Put it there" — put is an operation, a logical type. "What is put?" — put is data, a physical type. Same identifier, both dimensions always present. Self-description is built in: every operation is both invokable and queryable.

The system can function without full schema description. Code runs with short names. Properties hold values. The system is dirty with respect to its own self-knowledge — it functions, it just does not know what it is. Adding schemas is the same move as adding mutability metadata to a dirty fabric. The system gains insight into itself incrementally. No hard boundary between not ready and ready. Full description is needed for shared knowledge — for it to become shareable, it must pass through language interaction. But the insight is real without the schemas. The formal description catches up to what was already understood.
